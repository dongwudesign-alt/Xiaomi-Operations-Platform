## 一、功能定位

「角色与权限」是控制台的 **RBAC 配置中心**：定义角色、给角色绑定权限点，是「用户」模块分配角色的数据源。

功能边界：

- 维护**角色**（编码、名称、说明、权限点集合）。
- 维护**权限点**与角色的绑定关系（授权 / 撤权）。
- 不负责把角色分配给具体人，这一步在「用户」模块完成。
- 权限点本身由系统内置（代码中定义），本模块只能勾选组合，不能新增权限点（推断：权限点与业务功能一一对应，由开发侧维护）。

## 二、角色模型

### 角色属性

| 属性 | 说明 |
|---|---|
| 编码 | 角色唯一标识，如 `super_admin`、`model_operator`、`auditor`、`guest`，新建时手填（示例占位 `model_auditor`） |
| 名称 | 展示名，如"超级管理员""模型运营""审计员""游客" |
| 说明 | 角色职责描述，新建时选填 |
| 内置标记 | 内置角色带"内置"标识，与自建角色区分 |
| 权限点集合 | 该角色被授予的原子权限 |

### 内置角色

| 角色 | 编码 | 职责描述 | 权限特征 |
|---|---|---|---|
| 超级管理员 | `super_admin` | 拥有全部权限点 | 全量勾选且**不可裁剪**（页面明示"超级管理员拥有全部权限点，不能在这里裁剪"，复选框为锁定态） |
| 模型运营 | `model_operator` | 模型管理与审计查看 | 模型域全量 + 引擎域全量 + 元数据各域只读 + 审计只读；系统域与机型写、审批处置均未授予 |
| 审计员 | `auditor` | 只查看操作日志 | 仅 `audit.read`，其余全部未授予 |
| 游客 | `guest` | 没有任何业务权限 | 全部未授予；作为**未分配人员的默认角色**（文案："普通员工从未该进入后使用这个角色，直到管理员另行分配"） |

规则：内置角色可调整权限点（审计员、游客、模型运营视图均带"保存权限"入口），但超级管理员例外，其权限为系统硬约束。

## 四、授权规则

1. **权限点彼此独立，无继承**：`read` 与 `write` 成对存在但互不隐含。截图中模型运营在元数据、机型、审批域均为"读开写关"，说明系统允许只给查看权而不给变更权。
2. **最小授权**：默认全不勾选，由管理员逐项授予；不存在"授予某角色即自动获得全部下级权限"的规则。
3. **职责分离（SoD）**：模型运营被授予了模型/引擎的发布、下线、删除、吊销等执行权，但 `approval.decide` 未授予，即**执行者不掌握审批裁决权**，审批由其他角色处置，避免自批自审。
4. **审计独立性**：审计员只持有 `audit.read`，不持有任何业务写权，也不持有 `approval.read`，保证审计视角只依赖操作日志。
5. **管理权集中**：`system.role.write`（管理角色，等同可修改权限体系）仅超级管理员持有；模型运营与审计员均未授予。
6. **内置角色的默认语义**：游客是兜底默认角色（无任何权限），新进人员未分配前按此角色处理。

## 五、功能点

### 1. 查看角色权限

- 选择任一角色可查看其完整权限点矩阵：已授权为勾选，未授权为空。
- 每个角色附一行职责说明（如"模型管理与审计查看""只查看操作日志"），作为授权意图的约束说明。
- 超级管理员视图为全量锁定，用于确认权限清单的完整性。

### 2. 授权与撤权

- 对单个角色逐项勾选/取消勾选权限点，通过"保存权限"提交。保存为**按角色整体提交**，非单点即时保存。
- 保存后该角色权限即时对已绑定用户生效（推断）。
- 修改内置角色（非超管）的权限点属于允许操作。

### 3. 新建角色

| 字段 | 必填 | 规则 |
|---|---|---|
| 编码 | 是 | 唯一标识，建议 `域_职责` 形式（示例 `model_auditor`） |
| 名称 | 是 | 展示名 |
| 说明 | 否 | 职责描述 |
| 权限点 | 创建后再配 | 新建时不选权限，创建完成后进入角色再勾选 |

- 新建角色通过弹层创建，取消则不落库。
- 新建后的角色为空权限状态，需二次操作授权（推断）。

### 4. 权限生效链路

```
管理员配置角色权限 → 保存
      → 角色权限集更新
      → 绑定该角色的所有用户同步生效（推断）
      → 用户下次访问对应功能时按权限点校验（推断）
```

## 六、现有功能能力与缺口

已具备：

- 4 个内置角色 + 自建角色能力。
- 32 个原子权限点，覆盖模型、推理引擎、机型、审批、元数据、用户、角色七大域。
- 读写分离、最小授权、职责分离的授权模型。
- 超级管理员的全量锁定保护。

尚不具备或未体现：

- **角色的删除与改名/改说明**：页面未见删除或编辑角色名称的入口，内置角色与自建角色均无。
- **权限变更审计**：谁在何时修改了哪个角色的哪些权限点，未见记录入口（`audit.read` 是否存在覆盖需确认）。
- **权限对比**：两个角色间的权限差异对比未见。
- **角色复制**：基于现有角色快速克隆建新角色未见。
- **权限搜索/按域筛选**：32 个权限点平铺，无搜索。
- **角色的成员数展示**：无从得知某角色被多少人使用，改权限前的影响面不可评估。
- **权限变更的审批**：`system.role.write` 本身即高权操作，却未见审批环节（与「审批」模块未打通）。
- **按对象/数据范围授权**：权限点为功能级（能做/不能做），未见"只能操作某些模型/某些业务线"的数据级授权。

## 七、待确认事项

1. 角色编码创建后是否可改；重名或编码冲突如何处理。
2. 删除角色（尤其自建角色）是否支持；若角色仍绑定用户，删除时用户如何处理（回退游客？阻断？）。
3. 角色权限保存后是否需要用户重新登录才生效。
4. `meta.engine.read/write`（推理平台）与 `engine.*`（推理引擎）的业务区别，命名相近易混，需明确边界。
5. 一个人多角色时权限是**并集**还是存在互斥约束（推断为并集）。
6. 内置角色是否允许被改权限点；若允许，与"内置"语义是否冲突（现状：可改）。
7. `audit.read` 的可见范围是本人操作还是全平台操作，以及是否包含权限变更记录。
